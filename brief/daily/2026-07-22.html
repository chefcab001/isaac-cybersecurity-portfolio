CISA adds four exploited vulnerabilities as WordPress flaws form an RCE chain

July 22, 2026, Hawaii Standard Time. Public educational analysis published from the accepted daily intelligence brief.

Executive Threat Overview

The most important new development is CISA’s July 21 addition of four vulnerabilities to the Known Exploited Vulnerabilities Catalog:

  1. CVE-2026-60137, WordPress SQL injection
  2. CVE-2026-63030, WordPress interpretation conflict that can form an RCE chain with CVE-2026-60137
  3. CVE-2026-55255, Langflow authorization bypass
  4. CVE-2021-27137, DD-WRT UPnP stack-based buffer overflow

CISA added all four based on evidence of active exploitation. Two of the entries, the WordPress vulnerabilities, operate as a vulnerability chain and must be assessed individually as well as collectively. (CISA)

Additional material developments:

  • A newly disclosed Upbound Group incident allegedly enabled fraudulent lease-to-own agreements and contributed to approximately $13 million in fraudulent contract losses.
  • Independent researchers report exploitation of SharePoint CVE-2026-50522 following publication of proof-of-concept code, but CISA KEV inclusion was not verified as of this reporting cutoff.
  • NIST released the initial public draft of SP 800-209 Revision 1, Security Guidelines for Storage Infrastructure, for comment through September 8, 2026. (SEC)

Act Today

Priority 1: Patch and investigate the WordPress exploitation chain

CVE-2026-60137

WordPress 6.8.x before 6.8.6, 6.9.x before 6.9.5, and 7.0.x before 7.0.2 inadequately sanitize the author__not_in parameter of WP_Query. Exploitation depends on a plugin or theme passing attacker-controlled input into that parameter. (NVD)

CVE-2026-63030

WordPress 6.9.x before 6.9.5 and 7.0.x before 7.0.2 contain a REST API batch-routing interpretation conflict. When chained with CVE-2026-60137, it can permit SQL injection and remote code execution. (NVD)

Required action

For Federal Civilian Executive Branch organizations, the applicable CISA KEV remediation instructions and deadlines are mandatory under the controlling federal directives.

For other organizations, KEV inclusion is not automatically a legal mandate, but it is authoritative evidence of active exploitation and should trigger emergency risk-based action.

Recommended action

  1. Inventory all WordPress installations, including abandoned marketing sites and subsidiary-hosted instances.
  2. Record core version, hosting provider, plugins, themes, Internet exposure, administrator accounts, and business owner.
  3. Upgrade to the supported fixed branch.
  4. Preserve web, application, authentication, WAF, EDR, and hosting-provider logs before destructive remediation.
  5. Search for newly created administrator accounts, modified PHP files, web shells, unauthorized plugins, scheduled tasks, and unexpected outbound connections.
  6. Review vulnerable sites for plugins or themes that pass untrusted input to WP_Query.
  7. Rotate administrative credentials, database credentials, API keys, salts, and hosting credentials when compromise cannot be excluded.
  8. Validate site behavior, authentication, logging, and backups after remediation.

Risk if ignored

Unauthenticated remote code execution, database compromise, credential theft, website defacement, payment redirection, malware distribution, and persistence.

Confidence: HIGH

Priority 2: Review Langflow agent and workflow exposure

CVE-2026-55255

Langflow versions before the corrected release contain an authorization weakness involving user-controlled flow identifiers. An authenticated attacker may access or execute another user’s flow by supplying the victim’s flow ID. NVD references the Langflow GitHub security advisory, patch commit, and exploitation evidence. (NVD)

Exploitation Confirmed by CISA

Why it matters

Langflow is used to build AI agents, RAG applications, MCP services, workflows, and tool-connected applications. Compromising another user’s flow could expose:

  • API credentials
  • Model-provider tokens
  • Vector databases
  • Internal knowledge sources
  • Connected tools
  • Prompt and system instructions
  • Agent execution privileges

Langflow explicitly supports agent workflows, APIs, MCP servers, vector databases, and custom Python components, increasing the potential blast radius of improper authorization. (Langflow)

Recommended action

  • Identify Langflow servers, desktop instances, containers, development environments, and public API endpoints.
  • Confirm the exact fixed version from the vendor advisory before upgrading.
  • Restrict Langflow administration and API access to approved users and networks.
  • Review flow ownership and sharing permissions.
  • Rotate model, database, and service credentials exposed to shared flows.
  • Inspect audit and application logs for unauthorized flow ID access.
  • Require human approval before AI workflows invoke administrative or destructive tools.

Risk if ignored

Cross-user workflow execution, secret exposure, unauthorized agent activity, data disclosure, and movement into connected systems.

Confidence: HIGH for KEV status and the underlying authorization issue. EPSS confidence: LOW, because a current FIRST value was not independently retrieved.

Priority 3: Locate and replace vulnerable DD-WRT systems

CVE-2021-27137

DD-WRT builds before 45724 contain an unsafe strcpy operation in UPnP SSDP request handling. Exploitation requires UPnP to be enabled. UPnP is reportedly disabled by default and ordinarily listens internally, but exposed or poorly segmented devices remain at risk. (NVD)

Fortinet and other sources associate exploitation with the C0xM0 botnet. This is supporting technical reporting, not a basis for assuming every compromised DD-WRT router belongs to the same campaign. (NVD)

Recommended action

  • Discover consumer, laboratory, small-office, remote-worker, and unmanaged DD-WRT routers.
  • Confirm firmware build and UPnP status.
  • Disable UPnP where not explicitly required.
  • Prevent WAN access to management and UPnP services.
  • Upgrade to a supported fixed build or replace unsupported hardware.
  • Reset devices to known-good configurations if compromise is suspected.
  • Rotate wireless, administrative, VPN, and downstream credentials.
  • Review DNS settings, port forwards, startup scripts, firewall rules, and unauthorized accounts.

Risk if ignored

Botnet enrollment, remote code execution, DNS manipulation, credential interception, internal reconnaissance, and attacks against downstream systems.

Confidence: HIGH

Priority 4: Investigate SharePoint CVE-2026-50522 without overstating KEV status

Microsoft’s July 14 SharePoint updates address CVE-2026-50522 across supported on-premises SharePoint products. Microsoft’s SharePoint update pages identify prerequisite and post-installation requirements that must be reviewed before deployment. (Microsoft Support)

Independent researchers and honeypot operators reported successful exploitation attempts after public proof-of-concept code became available, including attempts to obtain IIS machine keys. CISA KEV inclusion for CVE-2026-50522 was not verified during this session. Therefore, this report classifies it as broader observed active exploitation, not as a newly added KEV entry. (The Hacker News)

Required distinction

  • Confirmed: Microsoft issued fixes.
  • Credibly reported: Independent researchers observed exploitation.
  • Not confirmed in this review: CISA KEV status.
  • Not proven by patching: Absence of prior compromise.

Recommended action

  • Confirm SharePoint product, edition, build, Workflow Manager dependency, and update prerequisites.
  • Back up the farm configuration and relevant databases.
  • Install supported security updates using Microsoft’s documented sequence.
  • Complete required configuration steps, including PSConfig where applicable.
  • Review IIS logs, SharePoint logs, process creation, machine-key access, web shells, assemblies, scheduled tasks, and outbound traffic.
  • Rotate machine keys, service credentials, application secrets, and relevant certificates when theft is suspected.
  • Rebuild compromised servers from known-good media rather than trusting patch-only remediation.

Risk if ignored

Remote code execution, machine-key theft, forged authentication tokens, persistent access, document exposure, and lateral movement.

Confidence: MODERATE to HIGH

Major Incident and GRC Finding

Upbound Group: stolen information allegedly enabled $13 million in fraud

Upbound Group filed a Form 8-K on July 21, 2026 stating that unauthorized parties obtained certain customer information and documents. The company believes information from some incidents was subsequently used to facilitate fraudulent lease-to-own agreements, contributing to approximately $13 million in elevated fraudulent contract losses in its Acima segment during the second quarter of 2026. (SEC)

The company reported:

  • Enhanced authentication controls
  • Additional fraud-detection and monitoring capabilities
  • Engagement of external cybersecurity experts
  • Notification to federal law enforcement
  • An ongoing investigation
  • A current determination that the incidents were not material

The filing was made under Item 8.01, not Item 1.05, while preserving the company’s commitment to reassess materiality if facts change. (SEC)

Why it matters

This incident demonstrates that information labeled “non-sensitive” can still have high operational value when combined with business-process knowledge.

The loss pathway appears to be:

Unauthorized information access → identity or transaction abuse → fraudulent agreements → direct financial loss

GRC implications

Organizations should not base classification solely on whether information contains Social Security numbers, payment cards, or regulated health information. Classification should also evaluate whether information can enable:

  • Account impersonation
  • Fraud
  • Social engineering
  • Contract creation
  • Workflow bypass
  • Customer verification circumvention
  • Business-process manipulation

Recommended action

  • Map customer data to the business actions it can authorize or facilitate.
  • Test authentication and fraud controls together rather than as separate programs.
  • Add transaction-risk signals to cybersecurity incident triage.
  • Establish escalation criteria for cumulative fraud losses.
  • Preserve materiality-analysis evidence and reassess as facts develop.
  • Review whether third parties can create or approve contracts using customer data alone.

Risk if ignored

Direct financial loss, fraudulent contracts, regulatory scrutiny, consumer harm, litigation, and inaccurate materiality conclusions.

Confidence: HIGH

NIST and GRC Update

Draft NIST SP 800-209 Revision 1

NIST released the initial public draft of SP 800-209 Revision 1, Security Guidelines for Storage Infrastructure, on July 22, 2026. Public comments are due September 8, 2026. (NIST Computer Security Resource Center)

Relevance

Storage infrastructure is central to:

  • Ransomware recovery
  • Immutable backups
  • Data-at-rest protection
  • Administrative separation
  • Replication security
  • Snapshot governance
  • Storage-network segmentation
  • Cloud and hybrid data resilience

Requirement versus recommendation

The draft is not yet a final NIST publication and is not automatically mandatory. It may influence federal baselines, procurement requirements, contractual controls, and organizational standards after review or finalization.

Recommended action

Storage, cloud, backup, security architecture, and GRC teams should compare the draft against:

  • Current storage architecture
  • Backup administration
  • Encryption and key ownership
  • Snapshot and replication controls
  • Administrative network separation
  • Recovery testing
  • Storage firmware and vulnerability management
  • Logging and anomaly detection

Confidence: HIGH

OT and ICS

No new July 22 CISA ICS advisory was independently validated during this review. The July 21 advisory set remains under applicability review.

Revision 5 requires that CISA ICS advisories not be reported from titles or rendered-page fragments alone. Product versions, severity, exploit prerequisites, and mitigations must be validated through the underlying advisory data and corresponding vendor source before entering a technical finding.

Current OT priorities remain:

  • Asset and firmware inventory
  • Vendor remote-access control
  • Passive monitoring
  • Controller and engineering-workstation backups
  • Network segmentation
  • Safety-reviewed change control
  • Tested restoration of logic and configurations

NIST’s June publications include an OT Backup Quick Start Guide and guidance for secure remote access in water and wastewater environments. (NIST Computer Security Resource Center)

Confidence: HIGH for the methodological conclusion. New product-specific finding: None entered

AI, Cloud, Identity, and Zero Trust

The Langflow KEV entry reinforces that AI platforms must be treated as application platforms with conventional authorization, isolation, logging, and vulnerability-management requirements.

Required controls

  • Inventory AI systems, agents, MCP servers, vector databases, and connectors.
  • Assign owners to every nonhuman identity.
  • Separate development, testing, and production flows.
  • Restrict access by user, tenant, and workflow ownership.
  • Store secrets in managed vaults rather than flows or prompt text.
  • Log cross-user resource access and tool invocation.
  • Require human authorization for external communications and destructive actions.
  • Test for insecure direct-object references, authorization bypass, prompt injection, and excessive agency.

Zero trust requires verified identity, resource-level authorization, least privilege, device or workload context, continuous evaluation, and rapid revocation. It is not established by purchasing an identity product or attaching “zero trust” to an architecture diagram.

Confidence: HIGH

Study Today

Focus lesson: Vulnerability chains change the risk calculation

CVE-2026-60137 may appear less urgent if assessed only through its CNA CVSS score and prerequisite conditions. CVE-2026-63030 changes the attack path by creating a route-confusion condition that can enable exploitation of the SQL-injection weakness.

Analytical rule

Never evaluate a vulnerability only as an isolated CVE when evidence indicates a practical chain.

Document:

  1. Each CVE individually
  2. Preconditions for each vulnerability
  3. The order of exploitation
  4. Combined impact
  5. Versions affected by each component
  6. Whether one patch resolves both
  7. Whether indicators differ by stage
  8. Whether the chain bypasses assumed compensating controls

Practical exercise

For one public-facing application, create this record:

Question Evidence
Which vulnerabilities apply? Vendor and NVD records
Can they be chained? Vendor or reproducible technical analysis
Is exploitation confirmed? CISA KEV or validated telemetry
What is the attack prerequisite? Technical advisory
What privilege is obtained? CVSS vector and technical evidence
What data or systems become reachable? Architecture and data-flow map
What is the supported fix? Vendor release
What compromise evidence should be collected? Logging and forensic plan

Questions Leaders Should Ask

  1. Do we operate WordPress 6.8, 6.9, or 7.0 systems below the fixed versions?
  2. Are abandoned, subsidiary, vendor-managed, or marketing WordPress sites included?
  3. Have we searched for compromise rather than only confirming patch deployment?
  4. Do any Langflow workflows contain reusable credentials or cross-user access?
  5. Which AI agents can execute another user’s workflow or invoke external tools?
  6. Are any DD-WRT routers running builds before 45724 with UPnP enabled?
  7. Are SharePoint machine keys and application secrets included in compromise-response procedures?
  8. Can customer information categorized as “non-sensitive” enable fraud?
  9. Does cybersecurity incident triage include financial-fraud monitoring?
  10. Are storage administrators separated from domain and backup administrators?
  11. Can ransomware operators delete or alter production snapshots?
  12. Which risk decisions rely on one CVSS score despite conflicting authoritative assessments?
  13. Which current KEV entries lack an identified asset owner?
  14. What evidence proves today’s remediation actually reduced exposure?

Bottom Line

Today’s new priority is the four-CVE July 21 CISA KEV update, led by the WordPress exploitation chain.

The correct operational sequence is:

PLAN → INVENTORY → VALIDATE EACH CVE → VALIDATE THE CHAIN → PRESERVE EVIDENCE → DOCUMENT CHANGE AND ROLLBACK → REMEDIATE → HUNT FOR COMPROMISE → VALIDATE SERVICE AND SECURITY → MEASURE → DOCUMENT RESULTS → STOP AND REASSESS
